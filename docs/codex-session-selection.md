# Codex conversation identity

Codex 0.162 can run several terminals through one shared background app-server. That server inherits the environment of the terminal that started it. Herdr's original SessionStart helper uses the inherited `HERDR_PANE_ID`, so a hook for another frontend can update the wrong pane's session ID.

New Codex chats created by Herdr Pocket use `codex --no-daemon`. This keeps the session and hooks in their own terminal, so Chat opens automatically once the exact session is reported. Pocket upgrades recognized versions of Herdr's pinned official helper: on Linux, hooks whose nearest Codex ancestor is `app-server` are ignored. The helper also requires that ancestor to match the reported pane's actual foreground process group and controlling terminal, using a bounded read-only Herdr query and owned process/socket checks. Stale inherited pane variables cannot redirect a report into another tab. Custom helper contents and other hook registrations are preserved. The updated phone requires the Linux-only `codex-create-isolated` capability for new chats; existing macOS chat and terminal access remain available.

For an existing shared-daemon terminal without a remembered choice, open Chat and choose the loaded conversation you want to control. Existing terminals and conversations continue running. The choice is explicit because Codex's public API does not report which thread each TUI is displaying; Pocket does not infer that association from a directory, title, recently updated file or the daemon's inherited environment.

Choices contain primary interactive conversation IDs, saved names, creation times and runtime status. Message previews and subagent histories are excluded. A CLI can resume a conversation created in VS Code or the desktop app, retaining its original `source: vscode`, so both `cli` and `vscode` origins are eligible. The selected thread must be loaded, non-ephemeral, have its own root session ID, have no parent thread and advertise direct input support.

Each selection is scoped to the paired phone's credential and pane. Choice tokens expire after five minutes and are accepted once, with the exact frontend/daemon/socket metadata rechecked before selection. Listing scans at most 256 loaded IDs over eight pages and displays at most 32 eligible choices within an eight-second daemon deadline.

Version 0.7.2 remembers at most 32 explicit choices in a private atomic ledger bounded to 32 KiB. It records credential hashes, pane IDs, canonical conversation IDs and identity digests, without conversation bodies, titles, raw paths or credentials. Restoration requires the same Linux boot ID, exact terminal, Herdr socket device/inode, foreground Codex PID/start time, daemon PID/start time, owned daemon socket path/device/inode and Codex home. Every restoration re-proves the live socket peer and verifies that the chosen thread is still loaded and eligible. Reconnecting endpoint socket inodes can change without changing the running process identity; companion restart and reconnect therefore preserve a verified choice. Process/terminal/daemon replacement or host reboot requires choosing again. Temporary unavailable peers or unloaded threads retain the recorded choice rather than selecting something else. After upgrading from 0.7.1, one initial choice may be necessary because that version's memory-only choices were not exported.

This remembers the chosen conversation; it does not follow the conversation displayed by the TUI. Codex can switch threads with `/new`, `/resume` or its agent picker while retaining the same PID, start time and socket connection. Its current thread lives in frontend memory, and no exact public mapping exposes it to Pocket. Optional terminal titles omit or truncate the UUID, and global loaded-thread listings cannot identify the active frontend thread. If you switch chats inside the terminal, use **Conversation** in Pocket to choose the intended target too. Automatic association for such existing shared frontends would require an upstream exact identity signal on each switch.

Selected chat reads use a separate connection to the existing daemon. A Send starts an idle turn with `turn/start` or steers a working turn with `turn/steer` and its exact `expectedTurnId`. Images use official `localImage` input. Existing frontend listeners remain attached and handle approval or tool questions in Terminal. Pocket never answers a server request automatically. A failed or missing acknowledgement is delivery uncertainty: Pocket does not retry the write, switch thread, start another runtime or fall back to terminal input.

The remembered choice retains its original binding-identity digest across verified reconnects and companion restarts. This preserves the scope of durable partial-attachment delivery markers even when the temporary HTTP binding rotates. Restoring a conversation or reading it successfully never acknowledges uncertain input, makes consumed attachment IDs reusable or retries a message. Delivery still requires explicit review and acknowledgement where indicated.

History normally uses one full `thread/read`. Only a typed response-size violation at the 32 MiB transport cap enables bounded `thread/turns/list` paging, starting with five turns and reducing oversized pages to two, then one. An oversized single turn uses Codex's official summary view and warns that only its first user message and last agent message are shown. Tool/reasoning items are discarded before retention; paging retains at most 1,024 turns and 64 MiB of visible structured data, warning when older history is omitted. Timeouts, permission errors and incompatible responses do not select summary mode.

Some existing daemons return the matched RPC error `-32601` with the exact message `list_turns is not supported yet`. Only that error enables a fallback to Pocket's separate saved-history reader for the same canonical UUID and Codex home. Delivery remains bound to the selected live daemon. The sidecar permits only initialization, `thread/read` and `thread/turns/list`; it never starts, resumes or sends a turn to an agent. Other daemon failures do not enable this fallback.

While Chat is visible, the phone retries failed reads after one, two, four, then eight seconds, preserving its transcript and draft. Authentication errors stop retries; leaving the foreground cancels reads. **Try now** requests an immediate read. Successful recovery closes only an automatically opened chooser for that same pane; a manually opened chooser and the guard against an unexpected conversation UUID remain in force. Send stays disabled during read recovery and uncertain delivery.
